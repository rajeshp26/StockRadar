# Checklist — G2 Impact Validation

Gate: `G2` · Layer: **existing** (§15.1) · Certifier: **Reviewer**
Governed by: spec §9.2, §6.11.
`CONDITIONAL`: permitted with a specific, owned, dated condition. Forbidden anywhere in an L4 feature.

> §15.1: existing gate. The lifecycle supplies F10 forward and reverse analysis plus `impacted_paths`; the existing definition governs enforcement.

## 0. Pre-checklist blocking checks

- [ ] Author and certifier identity blocks complete; identity rule satisfied (§9.1.1).
- [ ] Certified against the current requirements and contract baselines (§8.6 rule 5).

## 1. Forward impact — what does this change touch?

Each item answered or marked not applicable with a reason:

- [ ] requirements
- [ ] architecture
- [ ] components
- [ ] classes
- [ ] interfaces
- [ ] public APIs
- [ ] events
- [ ] database and schema
- [ ] configuration
- [ ] HMI
- [ ] apps
- [ ] backend
- [ ] vehicle services
- [ ] platform
- [ ] HAL
- [ ] build
- [ ] deployment and rollout
- [ ] security posture
- [ ] logging
- [ ] telemetry
- [ ] diagnostics
- [ ] documentation

## 2. Reverse impact — mandatory, and where regressions hide

A forward-only impact analysis **FAILS** this gate (§6.11).

For every symbol, contract, event, table, column, config key and file being modified:

- [ ] existing consumers enumerated
- [ ] existing features relying on current behaviour enumerated
- [ ] existing tests including regression suites enumerated
- [ ] existing documented behaviour enumerated
- [ ] The reverse section is non-empty. An empty reverse section FAILS.

## 3. Impacted paths → regression selection

- [ ] `trace.yml` `impacted_paths` populated with `changed`, `dependents`, `regression`.
- [ ] Every impacted path has at least one selected regression test.
- [ ] Zero `orphan impact` under §8.4.
- [ ] The impacted-path list was handed to the Verifier and reflected in `F5-test-analysis.md`.

## 4. Schema, config and migration

- [ ] Schema changes identified with forward and backward compatibility stated.
- [ ] Config key changes identified with default behaviour on absent keys.
- [ ] Where `persistent_data_change` is true, migration **and** rollback scenarios exist in F2.
- [ ] Migration has a tested rollback at L4 (§11).

## 5. Audio Settings instantiation

- [ ] Every changed setting key checked for existing readers across HMI, Audio Service, HAL, VACS and Audio Hub.
- [ ] Control-scope changes traced to every existing per-seat and per-vehicle expectation they alter — a scope change on an existing setting floors at L3 per `depth_floors`.
- [ ] Focus and ducking changes traced to every other feature that acquires focus or is duckable; these floor at L3.
- [ ] Alert, chime and warning audibility paths checked; if touched, the L4 floor applies.
- [ ] Backend sync schema changes checked for older vehicle software versions still writing the previous shape.
- [ ] Persisted per-user values checked for downgrade behaviour, not only upgrade.
- [ ] Regression selection includes at least one case on a surface with a real audio path where the audio path is touched.
