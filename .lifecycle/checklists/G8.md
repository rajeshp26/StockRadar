# Checklist — G8 Lifecycle Validation Readiness and Acceptance

Gate: `G8` · Layer: lifecycle (new) · Certifier: **Verifier**
Governed by: spec §9.2, §9.3, §12.2, §15.4.
`CONDITIONAL`: **forbidden** at this gate (§9.2). Forbidden anywhere in an L4 feature.

> **G8 brackets F16.** Part A is certified before validation begins; Part B after it completes. There is **no G9** — adding one would compete with H3 (§9.3).
>
> Naming (§9.2): the **Lifecycle Validation Readiness and Acceptance Gate**. Not VAL.1 itself.

## 0. Pre-checklist blocking checks

- [ ] Author and certifier identity blocks complete (§9.1.1).
- [ ] Certifier independent of requirements, design and code authors by `agent_id` and `session_id`.
- [ ] At L4: role and identity independence, and no prior-session contribution.
- [ ] Certified against the current baseline; zero `stale baseline` orphans.

---

# Part A — Validation readiness (before F16)

## A1. Upstream verification

- [ ] All development verification passed: G4 and G7 have PASS entries, plus G5 and G6 where the feature has a UI surface.
- [ ] No required gate for the declared depth lacks a PASS entry (`config.yml` `rules.required_gate_missing: BLOCK`).
- [ ] No `CONDITIONAL` verdict remains open on any feeding gate.

## A2. Evidence package

- [ ] Package complete and **reproducible** from the recorded commands and commit alone.
- [ ] Every item carries `claim`, `command`, `commit`, `environment`, `timestamp`, `result_file`, `checksum` (§9.1.2).
- [ ] Result files committed.

## A3. Defect disposition

- [ ] Every known defect dispositioned with a rationale.
- [ ] Every defect records `process_originated: true|false` (§12.2).
- [ ] Every **process-originated** defect has both a symptom correction and an **escape correction**.
- [ ] Non-process-originated defects have a symptom correction only. Absence of a checklist change is correct here, not a finding.

## A4. Validation environment and scope

- [ ] Customer-journey scenarios executable in the validation environment, and that environment is identified from `config.yml` `test_surfaces`.
- [ ] Every `critical` scenario has an F16 case (§9.3 Part A).
- [ ] Zero orphans across all ten §8.4 classes.

## A5. Audio Settings readiness

- [ ] Validation surface has a real audio path — `vehicle` preferred, `bench_hu` where a vehicle is unavailable, with the fidelity gap recorded.
- [ ] Real occupancy represented where per-seat or `shared_vehicle` behaviour is in scope.
- [ ] Account with real backend sync provisioned where per-user persistence is in scope.

# Part B — Validation acceptance (after F16)

## B1. Journey execution

- [ ] Every `JRN-*` in scope executed in the validation environment, with results.
- [ ] Every `critical` and `high` scenario case executed, with results.
- [ ] Validation evaluated **intended use**, not implemented behaviour — the question is whether this serves the customer in their environment.

## B2. NFR measurement

- [ ] Each `NFR-*` measured by its stated method.
- [ ] The **measured value** is recorded for each, not merely a pass assertion.
- [ ] Any NFR that could not be measured in this environment is listed as a residual limitation, not silently passed.

## B3. Findings classification

- [ ] Every F16 finding classified as: defect, requirement gap, or accepted limitation.
- [ ] Requirement gaps routed to F17 with escape point `requirement`.
- [ ] Defects routed to F17 with an escape point determined, not assumed to be implementation.

## B4. Residual limitations

- [ ] Every residual known limitation listed explicitly, each with its customer impact.
- [ ] No limitation left implicit or described only in prose elsewhere.

## B5. Evidence sealing

- [ ] Evidence package sealed: full file list with checksums, commit, environment.
- [ ] Seal is reproducible — recomputing checksums from the committed files matches.

## B6. Audio Settings acceptance

- [ ] Audible outcome confirmed by a real listener or a calibrated measurement on the real audio path, for every setting in scope.
- [ ] Per-seat isolation confirmed with real occupants.
- [ ] `shared_vehicle` driver override and co-pilot limit confirmed with two occupants.
- [ ] Focus and ducking confirmed against real concurrent sources, not stubs.
- [ ] Per-user restore confirmed across a real ignition cycle and a real account switch.
- [ ] Where alert, chime or warning audibility is in scope, audibility confirmed under the worst-case masking condition identified in §11 analysis.

## B7. Recommendation — not a decision (§9.3, §15.4)

- [ ] One recommendation recorded: `RECOMMEND_RELEASE`, `RECOMMEND_RELEASE_WITH_LIMITATIONS`, or `RECOMMEND_HOLD`.
- [ ] The entry states explicitly that **H3 owns the accept-or-reject decision**.
- [ ] Handover to H3 contains: sealed evidence package, this recommendation, and the residual-limitations list (§15.4).
- [ ] No release, ship or launch decision is asserted anywhere in this entry.
