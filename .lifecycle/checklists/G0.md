# Checklist — G0 Requirements Readiness

Gate: `G0` · Layer: lifecycle (new) · Certifier: **Reviewer**
Governed by: spec §9.2. Ledger format: §9.1. Identity rule: §9.1.1.
`CONDITIONAL`: **forbidden** at this gate (§9.2). Forbidden anywhere in an L4 feature.

## 0. Pre-checklist blocking checks

- [ ] Author identity block complete: `agent_id`, `role`, `session_id`, `timestamp`.
- [ ] Certifier identity block complete, and `certifier.agent_id != author.agent_id` **and** `certifier.session_id != author.session_id`.
- [ ] At L4 only: `certifier.role != author.role`, and certifier contributed nothing to F1–F3 in any prior session.
- [ ] Requirements baseline id assigned for this certification (§8.6 rule 1).

A missing identity field is a FAIL here, before any item below is read.

## 1. Use cases and journeys

- [ ] Every `CUS-*` identified, with separate ids per distinct customer.
- [ ] Every `UC-*` traces to at least one `JRN-*`.
- [ ] Journeys cover discovery, learning, invocation, recovery and abandonment.
- [ ] Every environment dimension in `config.yml` `environment_baseline` answered; none left "unknown".

## 2. Requirements completeness — four categories mandatory

- [ ] Functional `AC-*` present.
- [ ] Negative `AC-*` present.
- [ ] Boundary `AC-*` present.
- [ ] `NFR-*` present, each with a measurable threshold **and** a measurement method.
- [ ] A feature carrying only functional requirements FAILS here.
- [ ] No `AC-*` describes implementation.
- [ ] Every `AC-*` is independently verifiable.
- [ ] Every `AC-*` maps back to a `UC-*`.
- [ ] Every `SCN-*` maps to at least one `AC-*` or carries a recorded deferral with a reason.

## 3. Scenario risk ranking (§5.2.2) — v1.1

- [ ] Every `SCN-*` has `likelihood`, `impact`, `detectability` each 1–5.
- [ ] `priority` computed as `likelihood * impact * (6 - detectability)` and banded per `config.yml` `priority.bands`.
- [ ] Every `high` scenario has a planned F15 case, or a deferral with Reviewer concurrence.
- [ ] Every `critical` scenario has a planned F15 **and** F16 case, with no deferral.
- [ ] Risk scores were reviewed at F4 by an identity other than the F2 author.

## 4. Scenario selection discipline (§5.2.1)

- [ ] Combinations selected by named technique — equivalence, boundary, pairwise, state-transition, risk-based, or domain-mandatory — not Cartesian expansion.
- [ ] Each dimension appears in at least one scenario.
- [ ] Every applicable `class` value has at least one scenario.
- [ ] Unreachable combinations listed once with the reason.
- [ ] Asserted equivalence names the partition it relies on.

## 5. F4 findings

- [ ] Every F4 finding marked `blocking` or `non-blocking`, with an owner.
- [ ] Zero unresolved `blocking` findings.
- [ ] Zero unresolved ambiguities.

## 6. Audio Settings instantiation

- [ ] Each setting names its control scope from `config.yml` `control_scopes`: vehicle, seat or shared_vehicle.
- [ ] For `shared_vehicle` settings, the authority model states who may override whom, and the arbitration is referenced.
- [ ] Applicable `user_roles` named per `AC-*`: driver, co_pilot, normal, kids, guest.
- [ ] Audio-specific environment dimensions answered: active focus owner, ducking state, mute state, active zones, concurrent stream count, output endpoint set, amplifier/DSP variant, occupancy per seat.
- [ ] Where the setting affects alert, chime or warning audibility, the L4 floor from `depth_floors` was applied and §11 hazard and misuse analysis is present.
- [ ] Persistence dimensions swept in **both** directions — read and write. (Added by DEF-031, §12.3.)
- [ ] Audible-outcome criteria stated separately from state-readback criteria.
