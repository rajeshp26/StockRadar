# Checklist — G3 Architecture Validation

Gate: `G3` · Layer: **existing** (§15.1) · Certifier: **Reviewer**
Governed by: spec §9.2, §6.2, §6.5, §6.6, §6.7, §6.8, §6.10.
`CONDITIONAL`: permitted with a specific, owned, dated condition. Forbidden anywhere in an L4 feature.

> §15.1: existing gate. The lifecycle supplies F8, the ownership register, the concurrency model and the reuse records. The existing definition governs enforcement.

## 0. Pre-checklist blocking checks

- [ ] Author and certifier identity blocks complete; identity rule satisfied (§9.1.1).
- [ ] At L4: independent review of F8/F9 by a reviewer not involved in the feature (§11).
- [ ] Certified against the current requirements and contract baselines (§8.6 rule 5).

## 1. Interaction mechanisms named (§6.3)

- [ ] Every interaction names its mechanism from the allowed set: synchronous request/response, asynchronous command, query, event/notification, state exposure, callback, subscription, persistence operation, external API call.
- [ ] "Boxes and arrows" with no named mechanism FAILS.
- [ ] Sequence and ordering constraints stated per use case.
- [ ] What happens when a step fails mid-sequence is stated per use case.

## 2. Dependencies

- [ ] Dependencies explicit and their direction stated.
- [ ] Dependency graph acyclic.
- [ ] Failure boundaries defined, with degradation behaviour at each.

## 3. Cohesion, not operation counting (§6.2) — v1.1

- [ ] Every component has **one cohesive responsibility boundary**.
- [ ] Multiple operations within one boundary are permitted and are not flagged.
- [ ] Low-cohesion components are split; high-cohesion components are retained with a recorded justification.
- [ ] Zero `orphan component` under §8.4 — every `CMP-*` allocated to at least one `UC-*`.

## 4. State ownership register (§6.5) — mandatory at L2+

- [ ] Register exists and lists every mutable state.
- [ ] Each state has **exactly one** authoritative owner. Zero owners FAILS. Two or more owners FAILS.
- [ ] Readers enumerated per state.
- [ ] Writers enumerated per state, and only the owner writes.
- [ ] Persistence mechanism named per state.
- [ ] Synchronization mechanism named per state.
- [ ] Zero `orphan state` under §8.4.

## 5. Concurrency model (§6.6) — mandatory F8 artifact

For every concurrently mutable state, all nine recorded:

- [ ] ownership
- [ ] consistency model
- [ ] serialization mechanism — a model naming none FAILS
- [ ] conflict resolution — a non-deterministic winner FAILS
- [ ] ordering
- [ ] atomicity
- [ ] race prevention
- [ ] reentrancy
- [ ] thread safety

## 6. Design principles evaluated

- [ ] single responsibility
- [ ] high cohesion
- [ ] low coupling
- [ ] explicit dependencies
- [ ] dependency inversion where it buys testability
- [ ] interface segregation
- [ ] separation of concerns
- [ ] information hiding
- [ ] single clear ownership per piece of state
- [ ] determinism where required
- [ ] testability
- [ ] observability

## 7. Patterns justified (§6.8)

- [ ] Every pattern is from the allowed set: Strategy, State, Observer/Pub-Sub, Factory, Adapter, Facade, Command, Repository, Dependency Injection.
- [ ] Every use has a filled justification block: applied-to, why, alternative considered, decision, complexity cost.
- [ ] A pattern with no justification block is removed, not waived.

## 8. Reuse search — a hard check (§6.7)

Before any new service, event bus, repository, abstraction, utility, state manager, serialization format, retry mechanism or logging mechanism:

- [ ] `existing_mechanism.searched: true` recorded.
- [ ] `candidates` listed.
- [ ] `selected` and `reason` recorded.
- [ ] An unrecorded search FAILS.
- [ ] A bespoke mechanism duplicating an existing one FAILS unless the justification explains why the existing mechanism is unusable.

## 9. Design models — minimum necessary (§6.10)

- [ ] Every model present answers a stated design question. No diagram without one.
- [ ] Class diagrams are **not** mandatory and are absent unless they answer a question.
- [ ] State machines present wherever behaviour depends on lifecycle, asynchronous operations, transient state, retries, focus, connection, user switching or power transitions (§6.9).

## 10. Alternatives record — mandatory at L3+

- [ ] Alternatives table filled for every meaningful structural decision, across all ten criteria.
- [ ] Selected option marked, with the reason it beat the alternatives.
- [ ] At L2 the record is not required, since F8 is abbreviated to one page (Rule D2).

## 11. Audio Settings instantiation

- [ ] Every audio setting's authoritative owner named, and the owner is a single component.
- [ ] Control scope from `config.yml` `control_scopes` recorded per state: vehicle, seat or shared_vehicle.
- [ ] `shared_vehicle` states name their arbitration mechanism and a deterministic winner — driver override versus co-pilot limit.
- [ ] Focus and ducking state ownership sits with the arbitrator, not with the HMI.
- [ ] Concurrent device-versus-backend modification has a deterministic conflict winner recorded.
- [ ] Per-seat states show writer isolation: one seat's write cannot mutate another seat's value.
- [ ] Serialization across the IPC seams named in `config.yml` `layers` is stated, not assumed.
- [ ] A state machine exists for settings apply, focus transition, and account sync, since all three are temporal.
- [ ] Reuse search covered the existing settings repository, event mechanism and retry mechanism before any new one was proposed.
