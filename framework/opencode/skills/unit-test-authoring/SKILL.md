# Unit Test Authoring

A test that exists but cannot detect the defect it covers is not evidence. Test quality is measured by failure detection capability, not by test count.

## Mandatory workflow

```
Behavior (from acceptance criteria)
   ↓
Observable outcome (what changes)
   ↓
Test scenarios
   ├── happy path
   ├── boundaries (min, max, empty, zero)
   ├── invalid input
   ├── error handling
   ├── state transitions
   └── dependency failures
   ↓
Write test (RED phase)
   ↓
RUN TEST
   ↓
Verify it FAILS for the intended reason
   ↓
Implement (GREEN phase)
   ↓
RUN TEST
   ↓
Verify PASS
   ↓
Regression suite
```

## Critical rule: red before green

The framework does NOT consider:

```
test file exists + test passes
```

sufficient evidence.

The required evidence is:

> **The test was capable of detecting the missing/broken behavior.**

If you write a test and it passes before implementation, the test is not proving anything. Verify failure first.

## Oracle derivation (before you write the assertion)

Red-before-green proves the test *can* fail. It does not prove the value you assert
against is *correct* — a test fails-then-passes against a wrong expected value exactly
as reliably as against a right one. Failure-detection and oracle correctness are two
different properties. A passing test whose oracle was never independently established
is `weak_assertion` (see `framework/retro/containment_map.yaml`), not evidence.

Before asserting a value that isn't self-evident (a literal from the spec, a null
check), name how the expected value was obtained. Every non-trivial oracle uses one of:

| Method | Use when | What "correct" means here |
|---|---|---|
| Reference implementation | A simpler, independently-written path computes the same result | Diff against the reference across many inputs, not one |
| Golden fixture | Real domain data with a hand-verified expected output | The expected value was checked by a human against the domain — not generated by running the code under test |
| Differential / shadow | Porting, migrating, or reimplementing existing behavior | Diff against the old system's actual output |
| Invariant / property | A structural or algebraic law holds for ANY input (round-trip, idempotence, conservation, ordering, monotonicity) | No example value needed — assert the law, not a number |
| Hand computation | Small, bounded input where a human can derive the answer independently | Show the derivation in a comment; never derive it by running the code under test |

**Disqualifying an oracle** — none of these count as derivation:
- Copying the value the implementation currently returns into the test
- Asserting only shape, type, or non-emptiness when a specific value was computable
- Re-deriving the expected value with the same logic or library the implementation
  uses (that proves self-consistency, not correctness)

Record the method as a claim for any oracle backing a `high` or `medium` impact test.
The derivation is the author's self-report of process, so record it as an assumption —
a VERIFIED claim requires command provenance and would be rejected by the ledger:

python3 framework/claims/ledger.py append --json '{"task_id":"<task-id>","agent":"<agent>","statement":"<test name> oracle derived via <method>","claim_type":"data","classification":"ASSUMPTION","status":"UNVERIFIED","impact":"<high|medium|low>"}'

An assertion with no recorded derivation and no self-evident value is `weak_assertion`,
not `PASS` — regardless of whether it currently passes.

## Scenario coverage matrix

Every testable behavior MUST consider:

| Scenario class | Purpose | Required? |
|---|---|---|
| Happy path | Correct input, correct state, expected outcome | Always |
| Boundary | Edge values, empty collections, zero/one/many | When boundaries exist |
| Invalid input | Wrong types, missing fields, out of range | When input is user-provided |
| Error handling | Network failure, timeout, permission denied | When external dependencies exist |
| State transitions | Before/after state changes | When state is involved |
| Dependency failure | Mocked dependency returns error/empty | When dependencies exist |

Not every class applies to every behavior. When a class is omitted, state why.

## Test structure

```
describe "[behavior being tested]"
  it "does X when Y"
    given: [precondition]
    when: [action]
    then: [expected outcome]
    
  it "does Z when Y is absent"
    given: [precondition]
    when: [action]
    then: [expected outcome]
    
  it "handles error when W fails"
    given: [dependency will fail]
    when: [action]
    then: [error handled correctly]
```

## What makes a test good

- **Named after behavior**, not implementation (`"rejects expired tokens"` not `"test validateToken"`)
- **Isolated** — no shared state between tests
- **Deterministic** — same input always produces same result
- **Fast** — no network, no disk, no sleep
- **Self-contained** — reads and understands without external context
- **Failure-specific** — fails for the right reason, not by accident

## What makes a test bad

- Tests implementation details instead of behavior
- Depends on test execution order
- Has hidden external dependencies
- Passes when the code is wrong
- Fails for unrelated reasons
- Tests the mock instead of the code
- Always passes regardless of implementation
- Expected value copied from the implementation's own output instead of derived independently (see Oracle derivation)

## Assertion quality

Assert on observable outcomes, not internal state:

Good:
```
expect(result.isValid).toBe(true)
expect(error.code).toBe("EXPIRED")
expect(callCount).toBe(1)
```

Bad:
```
expect(internalMethod).toHaveBeenCalled()  // tests mock, not behavior
expect(result._private).toEqual(...)       // tests implementation detail
```
